# Dependency decision ledger

Record a row before implementing or materially expanding a capability. `Custom` is permitted only
with a link or quote identifying explicit owner authorization.

| Capability | Selected provider | Why this owns the mechanism | Status / re-evaluation trigger |
| --- | --- | --- | --- |
| JSON, reflected codecs, schema helpers | Glaze | One C++23/26 codec/reflection stack covers JSON and related formats. | Active; nlohmann/json removed after fixture parity. GCC 16.1 owns full codec/schema semantics. The pinned clang-p2996 fork is differential-only at the dependency-free P2996 adapter because it asserts inside Glaze's unrelated fallback field-name machinery. Re-evaluate the narrow boundary when the fork compiles the pinned Glaze release. |
| Operator HTTP API | Glaze HTTP | Existing ASIO HTTP/REST implementation avoids a local server/router. | Prototype gate: cancellation, TLS, size limits, overload, shutdown. |
| Codex JSON-RPC payloads | Glaze JSON facilities plus newline framing adapter | Existing codec facilities own JSON parsing and serialization; local code owns only Codex-specific DTOs, state sequencing, and JSONL process framing. | Active; additive-field and malformed-ID fixtures guard compatibility. |
| Workflow YAML | Glaze 7.9.0 YAML | The selected codec provides typed YAML 1.2 block/flow parsing, block scalars, generic provider subtrees, unknown-key policy, recursion bounds, and serialization without a second parser. | Adopted; `yaml-cpp` removed after synthetic shape, provider round-trip, repository `WORKFLOW.md`, GCC 16.1, ASan/UBSan, and TSan gates passed. Keep environment expansion, path policy, front-matter framing, and prompt semantics outside the codec. |
| Unit tests | `openalgz/ut` | Existing C++23 runtime/compile-time test framework replaces the local registry/macros. | Active through the pinned vcpkg overlay; GCC 16.1 CI is the release gate. |
| Dependency management | vcpkg manifest mode | Pinned registry, version graph, binary caching, and overlay mechanism. | Active; FetchContent/CPM/vendoring prohibited. |
| Development containers | Dev Container Specification plus `devcontainers/ci` `v0.3.1900000449` at `b63b30de439b47a52267f241112c5b453b673db5` | The maintained reference CLI/action owns devcontainer parsing, image construction, image metadata, lifecycle setup, cache routing, in-container commands, and post-success publication. | Adopt for both GCC 16.1 and clang-p2996. CI-specific build configs target the pinned Containerfile stages and use fresh, versioned GHA `mode=min` scopes so only layers required by the resulting images are imported/exported; `mode=max` intermediate compiler graphs exceed hosted-runner disk. Local configs consume explicitly published prebuilt tags. The action must run the full test command before its guarded post-success push. |
| Fast Source CI caches | `actions/cache` 5.0.5 at `27d5ce7f107fe9357f9df03efb73ab90386fccae` plus vcpkg's filesystem binary cache and ccache | The pinned Node 24 action owns GitHub cache transport; vcpkg owns ABI-keyed dependency archives; ccache owns compiler-result validity. This removes repeated provider builds without caching configured build trees or inventing a package service. | Cache vcpkg archives under the pinned dependency graph and restore a bounded GCC 16.1 ccache lineage per commit. Keep misses non-fatal, retain configure/build/test on every run, and rotate the key version when compiler or cache policy changes. |
| Dynamic memory and undefined-behavior analysis | GCC 16.1 AddressSanitizer plus UndefinedBehaviorSanitizer | The authoritative compiler already supplies maintained instrumentation and runtimes for heap/stack memory safety and undefined behavior, so a separate analyzer framework would duplicate the mechanism. | Run ASan+UBSan together in a dedicated GCC devcontainer preset with frame pointers and strict failure options. Keep TSan separate because sanitizer runtimes are not composed into one binary. |
| Formatting | `{fmt}` | Maintained type-safe formatting; compatible with future standard formatting. | Selected; use only after redaction. |
| Structured logging sinks | spdlog 1.17.0 from the pinned vcpkg registry | Its synchronous multi-sink logger, per-sink exception interception, per-logger error handler, and existing `{fmt}` integration provide the sink mechanism without adding a background runtime. | Adopt behind `EventStore`. Redact and retain the bounded status event before dispatch, count sink failures without recursive logging, and emit JSON as the unadorned payload. Re-evaluate only if required durability or asynchronous backpressure cannot be provided by configured spdlog sinks. |
| Async execution | NVIDIA stdexec `fee4d651494014610a277540f209cae56011e47f` behind a project execution seam | GCC 16.1 does not document native P2300 senders/receivers; the pinned registry package supplies the maintained C++26 reference model, static thread pool, value/error/stopped channels, and structured composition without a repository-owned executor. | Adopted from the curated port after exact GCC 16.1 provider and scheduler overlap gates. Keyed stop sources cancel individual invocations; only the scheduler drains completions and mutates run state. Executor capacity is fixed at daemon startup, so a live increase requires restart. Replace with the standard library once GCC provides the required surface. |
| SQLite access | `klemens-morgenstern/sqlite` | Typed queries, prepared statements, non-throwing APIs, RAII transactions/savepoints, hooks and backup. | Active through the pinned overlay. Synchronous calls stay on a one-thread NVIDIA stdexec pool; restart, invalid-envelope, concurrent-append, GCC 16.1, ASan/UBSan, and TSan fixtures passed. NVIDIA stdexec owns queued execution and cancellation; the repository applies a startup-fixed admission limit and returns a typed overload error before submission so accepted asynchronous work remains bounded. |
| Durable schema / repository | SQLite migrations plus repository-owned SQL | Durable domain schema is product-specific; wrapper owns mechanism, repository owns Symphony mapping. | Initial explicit versioned event envelope and ordered append/load repository are active. SQLite `user_version` records the committed schema level; startup applies ordered forward migrations transactionally and rejects databases newer than the executable. Pinned sqlgen 0.6.0 failed the deletion gate because its documented write path auto-creates schema from reflected structs, exposes `rfl::Result`, adds reflect-cpp/CTRE/yyjson, and supplies no cancellation boundary. Re-evaluate only if it adds an explicit-migration/manual-schema mode that deletes measured mapper code without introducing a second reflection or result authority. |
| Durable structured-event fanout | Thin adapter over `EventStore` and `EventRepository` | Redaction, JSON rendering, bounded async admission, serialized execution, and SQLite durability are already owned by selected components; the adapter owns only the Symphony mapping and failure accounting. | Fixture gate: redact before both sinks, retain the operator event when persistence overloads, count immediate and completion failures, and drain accepted work before destruction. Do not add another queue, serializer, logger, or database API. |
| Child process lifecycle | Boost.Process v2 1.91.0 | Its Asio-native process, stdio, EOF, working-directory, child-environment initializer, wait, and cancellation facilities replace repository-owned fork/exec/pipe/environment/wait mechanics. The pinned GCC 16.1 gate covers separate stdout/stderr, explicit EOF, start-directory, filtered environment, termination, and reap fixtures. | Adopted. Snapshot the child environment before concurrent workers start, remove every secret name published by registered tracker profiles, and pass the remaining entries through `process_environment`; preserve Codex-required non-secret variables. Use a dedicated Asio stderr pipe for a bounded tail while stdout remains authoritative. Keep Boost types behind the adapter. Process-tree/group cancellation remains an owner-gated hardening extension. |
| Workspace key and path containment | PicoSHA2 1.0.1 plus C++26 string/filesystem facilities behind `WorkspaceExecutor` | The curated, MIT, header-only dependency owns SHA-256; the standard library owns portable path resolution and inspection; Draft v1 owns allowed-character replacement and the stable original-identifier hash rule. | Active. Preserve `[A-Za-z0-9._-]`, append 128 SHA-256 bits when replacement is required, make `.`/`..` safe, and revalidate immediately before every hook or removal. Fixture and local executors must pass the same containment contract. |
| CLI parsing | CLI11 2.6.2 from the pinned vcpkg registry | Glaze 7.9.0's CLI facility is an interactive reflected menu rather than an argv parser. CLI11 directly owns strict positional/option parsing, subcommands, standard help, parse diagnostics, and exit codes without runtime dependencies. | Adopt behind executable-specific option structs. Keep workflow loading and process lifecycle outside the parser; re-evaluate if Glaze adds an equivalent argv contract. |
| Exact decimal arithmetic | Boost.Decimal | Existing IEEE decimal types. | Add only when an upstream contract requires exact decimals. |
| Symphony domain transitions and scheduler policy | OpenAI Symphony Draft v1 implemented locally | Normative product behavior has no reusable conforming C++ implementation in the recorded search; the owner explicitly approved the standalone C++ plan. | Keep pure and fixture-driven; commodity mechanisms still require dependencies. |
| Tracker adapter contract and normalization | C++26 `std::expected` plus Glaze DTO facilities behind the provider-neutral tracker seam | The Draft v1 issue model, adapter profiles, pagination safety, and error taxonomy are Symphony integration policy; standard vocabulary types carry failures without a custom result framework, while the selected codec will own future provider payload decoding. | Fixture-only contract active. Live HTTP remains disabled until the recorded Glaze HTTP client gate passes; do not add a second JSON or transport stack. |
| Development-work orchestrator | OpenSymphony `v2.10.0` as an external tool | It supplies Linear-driven scheduling, isolated issue workspaces, retries, recovery, Codex harnessing, and operator surfaces while leaving the standalone C++ product implementation independent. | Owner-approved bounded adoption. Run only in a containment boundary with the Codex harness; never link or vendor Rust into `symphony-cpp`. The dedicated Linear project is selected; worker activation remains gated on one-command secret injection, contained Codex login, healthy dry run, and one explicitly activated fixture-only canary. |
| Coding-worker model policy | Codex CLI model catalog, app-server pass-through fields, and repository-owned non-secret config overlay | Codex's versioned schema owns model/effort vocabulary. OpenSymphony can select one model but exposes no effort route in v2.10.0, while the standalone app-server accepts `model` and `effort` per turn. | Use the verified Sol/high baseline for both paths. Standalone C++ selects workflow-configured escalation/ceiling values between worker sessions after abnormal, repeated-failure, or no-progress evidence and de-escalates only on a changed progress fingerprint; never duplicate the Codex catalog. OpenSymphony remains operator-adjusted until it exposes an equivalent bounded route. |
| Coding-worker context rollover | Codex app-server cumulative token/context telemetry plus repository-owned session policy | Codex owns token measurement and compaction; Symphony owns the product decision to stop sending continuation turns before a configured percentage of the reported context window. No commodity scheduler can make this repository-specific transition. | Apply only between completed turns when both cumulative tokens and a positive model context window are reported. Keep observed-compaction rollover as the fail-safe; never estimate missing telemetry. |
